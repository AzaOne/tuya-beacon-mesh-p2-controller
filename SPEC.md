## 1. Система та межі довіри

**Фізична лампа** приймає короткі BLE Advertising-повідомлення від уже прив'язаного телефона. Для звичайних дій не встановлюється стале з'єднання GATT. Передавач може бути смартфоном Android або Linux Bluetooth-адаптером; після знання ключів потрібен лише сумісний BLE-радіоінтерфейс.

**Адреси** — це адреси *всередині P2 кадру*, не MAC-адреси Bluetooth. У найсвіжішому захопленні:

- `src = 0x7A59` — логічне джерело, яке використовував телефон.
- `dst = 0x0003` — логічна адреса лампи.
- `seq` у перевіреному журналі закінчується біля `0x008E` (це історичне значення, НЕ актуальний стан лампи).
- `head = 0x0B`, `subcmd = 0x05` — DP-команди керування, підтверджені пакетом.

У старіших записах були інші адреси, зокрема `src = 0x7DF9`, `dst = 0x0005`. Повторне спарювання може змінити адресу і ключі, тому не вважайте ці числа сталими між різними прив'язками.

`device_id` та Tuya Product ID — ідентифікатори хмарної екосистеми; **вони не передаються відкритим текстом у кожному командному P2-кадрі**.

## 2. BLE Advertising: саме 31 байт

Повний advertising data в цьому дослідженні становить **31 байт**:

```text
OFFSET  HEX       Що означає
00      02        довжина першої AD-структури: type + 1 байт даних
01      01        AD Type 0x01 = Flags
02      01        значення Flags з перевіреного варіанта
03      1B        довжина другої AD-структури: type + 26 байтів даних
04      03        AD Type 0x03 = Complete List of 16-bit Service UUIDs
05..30  ...       26 байтів Tuya P2 frame (НЕ звичайний список UUID)
```

Друга структура використовує поле «16-bit Service UUID list» як контейнер для сирого P2-кадру; операційна система може намагатися трактувати кожні два байти як UUID. Для сумісності потрібні *точні байти*, а не логічно еквівалентна колекція UUID, яку BlueZ може відсортувати чи перекодувати.

Спостерігалися варіанти Flags `0x01`; інші реалізації можуть використовувати `0x06`. Перемикач `-flags 01|02|06` дозволяє тестувати, але не доведено, що для цієї лампи всі варіанти еквівалентні.

**Плутанина HCI/ефіру:** Android використовує команду HCI `LE Set Extended Advertising Data` з opcode `0x2037`, але це **не означає**, що радіоефірне повідомлення обов'язково є extended advertising. Тут фактично формувалися legacy-розмірні пакети 31 байт.

## 3. Кадр P2 (26 байтів)

Усі `src`, `dst`, `seq` — **big-endian (старший байт спочатку)**.

```text
  idx   len  field             значення/опис
  ──────────────────────────────────────────────────────────────────
  00    1    head              0x0B для DP data frame
  01    2    src               0x7A59 (поточне спостережене джерело)
  03    2    dst               0x0003 (спостережена адреса лампи)
  05    2    seq               16-бітний лічильник
  07    1    subcmd            0x05 у TX-командах телефона
  08    1    data_crc          CRC16HI(plaintext[0:16])
  09    16   ciphertext_xored  XXTEA(plaintext, local_key) XOR beacon_key
  25    1    transport_crc     CRC16HI по ще НЕ XOR-маскованому кадру
  ──────────────────────────────────────────────────────────────────
                Разом 26 байтів
```

Інші спостережені заголовки/підкоманди в загальному семействі: `0x13` (service/bind/query), `0x93` (pair request), `0x9B` (pair response), `0x88` (idle/незашифрований), `0x02` як зворотний status subcmd. **Цей проєкт не стверджує, що вміє повністю розбирати або генерувати їхній payload**. Для користувацьких команд підтримуються тільки `head=0x0B`, `subcmd=0x05`.

## 4. Ключі: K1 і K2

Маємо **два незалежні 16-байтові секрети**:

- `K1 = local_key`: матеріал ключа XXTEA; для конкретної лампи Tuya Cloud повернув рядок із **16 ASCII-символів**. Навіть якщо ці символи схожі на hex, **не** слід декодувати рядок із 16 символів як 8 байтів!
- `K2 = beacon_key`: **16 байтів**, збережені як **32 hex-символи** в JSON. Це XOR-маска після XXTEA, не ключ XXTEA. Утиліта також допускає 16 ASCII-символів як альтернативне представлення, але в дослідженому випадку K2 отримано у hex.

```text
local_key  (16 ASCII)     ────────────────────┐
                                          ▼
plaintext16 ──────────► XXTEA-BE ENCRYPT ──► E(16)
                                          │
beacon_key (16 raw bytes) ──────────────── XOR ───► transmitted frame[9:25]
```

Після повторної активації облікові дані **можуть змінюватися**. Старий `local_key` із попереднього спарювання не дозволяв узгоджено відновити `beacon_key`, а актуальний ключ — дозволив відтворити 84 кадри захоплення. Це сильна емпірична ознака ротації K1, а не доказ того, що кожне спарювання обов'язково ротує всі ключі.

Ключі **не входять** до ZIP та тестових фікстур. Зберігайте їх локально у файлі `0600`. Не публікуйте raw HCI-журнали без перевірки вмісту: вони можуть містити чутливі дані інших BLE-пристроїв.

## 5. CRC16HI — не CRC16-XMODEM

Використовується функція, що повертає **верхній байт** внутрішнього 16-бітного стану. Відома реалізація (бітовий алгоритм із `internal/p2/protocol.go`):

```go
func crc16hi(data []byte) byte {
    var s uint16
    for _, b := range data {
        s ^= uint16(b) << 8
        for j := 0; j < 8; j++ {
            if s&0x8000 != 0 {
                s ^= 0x8380
            }
            s <<= 1
        }
    }
    return byte(s >> 8)
}
```

- Початковий стан `s = 0`.
- З кожним наступним байтом: `s XOR (byte << 8)`.
- Вісім ітерацій із перевіркою bit 15, XOR `0x8380` при встановленому bit 15 та зсувом вліво.
- Повертається лише `s >> 8`. Це **один контрольний байт**, а не повні 16 біт.

Використовуються **два окремі контролі**:

**CRC plaintext** у `frame[8]`:

```text
data_crc = CRC16HI(plaintext16)
```

**CRC транспортного кадру** у `frame[25]`:

```text
E = XXTEA_Encrypt_BE(plaintext16, K1)
frame[9:25] = E                 // ДО XOR!
transport_crc = CRC16HI( [frame[0] & 0xFC] || frame[1:25] )
frame[25] = transport_crc
frame[9:25] = E XOR K2         // XOR ЗАСТОСОВУЄТЬСЯ ПІСЛЯ CRC
```

Вхід у другу CRC — рівно **25 байтів**: один модифікований `head` та 24 наступні байти `frame[1]`…`frame[24]`. **Не включайте `frame[25]`** і не обчислюйте її за вже XOR-маскованим payload: отримані байти будуть неправильними.

CRC потрібна для виявлення випадкових помилок та відсіювання хибного дешифрування. **CRC не є MAC або криптографічним доказом автентичності**.

## 6. XXTEA-BE для plaintext із 16 байтів

Застосований варіант **XXTEA, 4 слова × 32 біти, BIG-ENDIAN**, без довільного префікса довжини. Він відрізняється від обгорток XXTEA, які пакують слова little-endian, додають length/padding або модифікують число раундів.

### Пакування слів

```text
plaintext bytes P[0..15]
  v[0] = BE32(P[0:4]);  v[1] = BE32(P[4:8]);
  v[2] = BE32(P[8:12]); v[3] = BE32(P[12:16]);

key bytes K1[0..15]
  k[0] = BE32(K1[0:4]); k[1] = BE32(K1[4:8]);
  k[2] = BE32(K1[8:12]);k[3] = BE32(K1[12:16]);
```

`n = 4`, `DELTA = 0x9E3779B9`, число раундів `6 + floor(52/n) = 19`.

### Функція змішування

Усі операції над `uint32`, тобто після додавання або віднімання — за модулем `2^32`. `^` означає XOR, `>>` та `<<` — логічні зсуви:

```text
MX(sum, y, z, key, p, e) =
     ( ((z >> 5) ^ (y << 2)) + ((y >> 3) ^ (z << 4)) )
   ^ ( (sum ^ y) + (key[(p & 3) ^ e] ^ z) )
```

### Шифрування (точний порядок)

```text
sum = 0
z = v[3]
repeat 19 times:
    sum = sum + DELTA
    e = (sum >> 2) & 3
    for p = 0..2:
        y = v[p+1]
        v[p] = v[p] + MX(sum,y,z,key,p,e)
        z = v[p]
    y = v[0]
    v[3] = v[3] + MX(sum,y,z,key,3,e)
    z = v[3]

output = BE32(v[0]) || BE32(v[1]) || BE32(v[2]) || BE32(v[3])
```

Зверніть увагу: `z` **оновлюється після кожного слова**. Якщо використати інший порядок оновлення `y/z`, результат не збігатиметься із записами Smart Life.

### Розшифрування (обернена процедура)

```text
sum = uint32(19 * DELTA)
y = v[0]
repeat 19 times:
    e = (sum >> 2) & 3
    for p = 3..1:
        z = v[p-1]
        v[p] = v[p] - MX(sum,y,z,key,p,e)
        y = v[p]
    z = v[3]
    v[0] = v[0] - MX(sum,y,z,key,0,e)
    y = v[0]
    sum = sum - DELTA
```

Реалізації, що відповідають цій специфікації, містяться в `EncryptXXTEABE()` (`internal/p2/protocol.go`) і `decryptXXTEABE()` (`internal/p2/decode.go`). Усі тестові ключі в репозиторії вигадані.

## 7. Генерація TX-пакета: повний алгоритм

Нехай команда — `ON` із одним DP, а `src`, `dst`, `seq` задані окремо.

1. Зібрати **16-байтовий** plaintext DP-блока (`01 11 01` + 13 нулів).
2. Обчислити `data_crc = CRC16HI(plaintext16)` і записати у `frame[8]`.
3. Обчислити `E = XXTEA_BE_ENCRYPT(plaintext16, K1)`.
4. Заповнити `frame[0:9] = head || src || dst || seq || subcmd || data_crc`.
5. Тимчасово записати `frame[9:25] = E` **без XOR**.
6. Обчислити `frame[25] = CRC16HI((head & 0xFC) || frame[1:25])`.
7. Записати `frame[9:25] = E XOR K2`, лишивши попередньо обчислену CRC без зміни.
8. Обгорнути frame у AD: `02 01 FLAGS 1B 03 || frame26`.
9. Передати advertising на вибраному `hciN`, повторити зі **свіжим `seq`**.

Псевдокод:

```text
function make_p2_command(src,dst,seq,plaintext16,K1,K2,flags):
    assert len(plaintext16)==16
    frame = byte_array(26)
    frame[0] = 0x0B
    frame[1:3] = BE16(src)
    frame[3:5] = BE16(dst)
    frame[5:7] = BE16(seq)
    frame[7] = 0x05
    frame[8] = CRC16HI(plaintext16)
    E = XXTEA_ENCRYPT_BE(plaintext16,K1)
    frame[9:25] = E
    frame[25] = CRC16HI( (frame[0] & 0xFC) || frame[1:25] )
    frame[9:25] = XOR(E,K2)
    return 02 01 flags 1B 03 || frame
```

**Важлива емпірична ознака:** `seq` розташований у незашифрованому заголовку. Для однакового plaintext і тих самих ключів 16 байтів `frame[9:25]` **однакові** незалежно від `seq`; натомість транспортна CRC змінюється. Внутрішній `seq` в plaintext цією версією протоколу **не підтверджений**.

## 8. Розбір RX-пакета

Для верифікації отриманого кадру:

1. Переконатися, що advertising дійсно містить AD Type `0x03` довжиною `0x1B` і 26 байтів даних.
2. Переконатися в сумісному `head = 0x0B`, `subcmd = 0x05` і правильних логічних `src`, `dst`.
3. Відновити **немаскований** шифртекст `E = frame[9:25] XOR K2`.
4. Тимчасово замінити масковані байти в копії кадру на `E`; перевірити транспортну CRC.
5. Розшифрувати `plaintext16 = XXTEA_DECRYPT_BE(E,K1)`.
6. Перевірити `CRC16HI(plaintext16) == frame[8]`.
7. Лише тепер розібрати DP-TLV, перевірити довжини й нульовий залишок.
8. Лише після всіх перевірок дозволено оновлювати `seq` та логічний стан у файлі.

Не можна сліпо «синхронізувати» `seq` з усіх рекламних пакетів: сторонній або пошкоджений пакет міг би підвищити лічильник до `0xFFFF`. `monitor` приймає тільки кадри, що пройшли перевірку ключами та CRC.

## 9. Як відновлюється `beacon_key`

Це **known-plaintext recovery для постійної XOR-маски**, а не «злам XXTEA».

Відомі:

- дійсний `local_key` (K1) із власного Tuya Cloud API;
- запис TX-кадру з Android;
- припущення про відомий plaintext команди, наприклад `ON = 01 11 01 00 ... 00`;
- шифрований маскований блок `C = frame[9:25]`.

Тоді для кожного байта `i`:

```text
E = XXTEA_BE_ENCRYPT(known_plaintext,K1)
K2_candidate[i] = C[i] XOR E[i]
```

Перевірка:

1. Знайти кандидатів із кількох кадрів ON та OFF, які мають відповідну `data_crc`.
2. Визначити кандидата, що повторюється незалежно від `seq`.
3. Застосувати його до **інших**, бажано різних DP-команд.
4. Перевірити **обидві** CRC і розбір DP для незалежних кадрів.
5. Не вважати успіхом одиничний збіг CRC: один байт дає лише 8 біт перевірки.

`tuya-beacon-mesh-p2-controller learn <android.cfa>` реалізує цей метод із журналом Android, а `tuya-beacon-mesh-p2-controller learn live` — **з реально прийнятих ПК BLE Advertising пакетів**. Для live-режиму використовується той самий приймач Linux HCI Monitor, але криптографічна перевірка робиться після накопичення кандидатів: ще не відомий `beacon_key` для первинного захоплення не потрібний. Обидва варіанти вимагають актуальний K1. Утиліта **не модифікує** основний JSON автоматично; збереження K2 дозволене лише при `-learn-out path`, де новий файл створюється з `0600` і не перезаписує існуючий. Окремий `cloud local-key` у v6 може отримати K1 із Tuya Cloud API.

Досліджений актуальний `local_key` і відновлений K2 дозволили побайтово відтворити **84** перевірені TX-кадри зі свіжого HCI-захоплення. Самі секрети навмисно не наводяться в цьому документі.

## 10. Формат DP-TLV

Блок шифрування завжди **16 байтів**. Усередині — одна або кілька послідовних записів TLV:

```text
DP = [id:1] [type:4 bits | length:4 bits] [value:length]
```

- `id`: 8-бітний ідентифікатор DP. У досліджених кадрах `id >= 1`; `0x00` на межі TLV інтерпретується як кінець/нульове доповнення.
- `type`: верхні 4 біти другого байта; значення залежать від виду DP.
- `length`: нижні 4 біти другого байта, діапазон 0..15, але кожен запис має повністю вміщуватися в межах 16 байтів.
- `value`: байти DP; значення типу `value` (DP3, DP4) у записах — **uint32 big-endian**.
- Решта 16-байтового блока доповнюється нулями.

### Приклади реальних одиночних DP

```text
ON:              01 11 01 00 00 00 00 00 00 00 00 00 00 00 00 00
OFF:             01 11 00 00 00 00 00 00 00 00 00 00 00 00 00 00
Режим white:     02 41 00 00 00 00 00 00 00 00 00 00 00 00 00 00
Режим colour:    02 41 01 00 00 00 00 00 00 00 00 00 00 00 00 00
Режим scene:     02 41 02 00 00 00 00 00 00 00 00 00 00 00 00 00
Яскравість 1000:03 24 00 00 03 E8 00 00 00 00 00 00 00 00 00 00
Температура 1000:04 24 00 00 03 E8 00 00 00 00 00 00 00 00 00 00
Зелений HSV:    0B 04 00 78 64 64 00 00 00 00 00 00 00 00 00 00
Синій HSV:      0B 04 00 F0 64 64 00 00 00 00 00 00 00 00 00 00
```

### Об'єднання кількох DP: v5

Пакувальник `packCommands()` послідовно переносить цілі DP-TLV, не розриваючи TLV на межі 16 байтів. Якщо наступний TLV не вміщується — відкриває наступний блок. Це пришвидшує композиції `rgb`, `temp`, `white`.

Приклад **режим colour + HSV(120,100,100)** — *синтетичний правильно закодований пакет*, але приймання цієї комбінації фізичною лампою ще не перевірено:

```text
02 41 01 | 0B 04 00 78 64 64 | 00 00 00 00 00 00 00
   3B    +          6B         +          7B       = 16B
```

**Режим white + DP4 (4000K) + DP3 (80%)**:

```text
02 41 00 | 04 24 00 00 01 56 | 03 24 00 00 03 20 | 00
   3B    +         6B          +         6B          + 1 = 16B
```

У другому прикладі `DP4=0x156=342` — результат **умовної** шкали `2700..6500 K → 0..1000`; це не фізично виміряна температура лампи. Для точної шкали використовуйте `temp-raw`.

За сумнівів у підтримці multi-DP — запускайте з `-multi-dp=false`: тоді кожний DP передається окремими блоками, як у перевірених Android кадрах.

## 11. Карта DP дослідженої лампи

| DP | Type | Value | Значення | Статус |
|---|---:|---|---|---|
| 1 | `1` | `00` / `01` | Вимкнути / увімкнути | **Спостережено**; OFF **спрацювало на лампі** |
| 2 | `4` | `00`, `01`, `02` | White / Colour / Scene | **Спостережено** |
| 2 | `4` | `03` | Music (?) | **Не підтверджено**; експеримент |
| 3 | `2` | `uint32 BE`, 10–1000 | Яскравість | **Спостережено** |
| 4 | `2` | `uint32 BE`, 0–1000 | Колірна температура (внутрішня шкала) | **Спостережено** |
| 11 | `0` | `BE16(hue), u8(s), u8(v)` | HSV колір | **Спостережено** |
| інші | різні | різні | Не виведено з журналу | Доступні лише експериментальні `dp` / `raw` |

Команда `rgb R G B` перетворює RGB 0..255 у HSV:

- Hue (`h`) — цілий кут 0..359°, два байти big-endian.
- Saturation (`s`) — ціле 0..100%.
- Value (`v`) — ціле 0..100%.

`rgb 100 232 111` → приблизно `HSV(125,57,91)`. Для закінченої команди колірного режиму спочатку застосовується DP2, потім DP11 — окремо в legacy mode або разом у multi-DP mode.

Не плутайте **DP2 «scene mode»** із вибором конкретної сцени: сцена передається окремим **DP73 `strip_scene` (тип 0, RAW)**. Зіставлення та шаблони описані нижче.

## 12. `seq` та anti-replay

`seq` — **16-бітне поле big-endian** у відкритому заголовку `frame[5:7]`. Ідентична команда може повторюватися з кількома новими послідовними `seq`: у захопленні Smart Life спостерігалися серії з чотирьох кадрів на дію.

**Що відомо:** попередня спроба локального `OFF` працювала, а `ON` зі старішим `seq` — ні. Це **узгоджується** з anti-replay, але не доводить точний алгоритм порівняння у прошивці. Пропущений рекламний пакет також пояснює різну реакцію.

**Політика програми (консервативна, а не твердження про SDK):**

1. Визначити останній відомий використаний/побачений `seq`.
2. Перед відправленням **зарезервувати та синхронно записати на диск** увесь діапазон для цієї команди.
3. Захистити state через `flock` та атомарний `rename`, з правами `0600`.
4. Окремий `.tx.lock` утримувати до закінчення всього надсилання, щоб паралельний CLI не випередив попередній.
5. Перехоплювати телефонні P2-команди; лише валідні криптографічно пакети з **новішим** `seq` просувають high-water mark.
6. **Не** зменшувати `seq` і **не** використовувати повторно вже зарезервовані значення після аварії чи радіопомилки.
7. На `0xFFFF` **зупинитися**, не здійснюючи автоматичного wrap у `0x0000`, доки поведінка лампи не доведена.

У файлі `./state/state-<device-id>.json` відносно робочого каталогу зберігаються `device`, `last_reserved`, відбиток ключів і optional `light`: останній **логічно відомий** стан. Секретні ключі в `state` не пишуться. Поле `confirmed=false` нагадує: перехоплений або надісланий advertising **не є ACK від лампи**.

`src` та `seq`: інші P2-проєкти використовували власне `src=0x8001`, але на цій лампі незалежність лічильників для різних джерел **не перевірена**. В `-src` можна вибрати інше джерело тільки як експеримент; `-phone-src` окремо вказує джерело телефона для монітора/аналізатора. Ідентичність конфігурації контролюється відбитком, щоб після репарингу випадково не використати старий лічильник з новими ключами.

## 13. HCI: спостереження телефона

### Android .cfa / .log

У стандартних Bluetooth HCI BTSnoop H4 файлах кожен запис має:

```text
file header: 16B = "btsnoop\0" + version + datalink
record: original_length(4 BE) + included_length(4 BE)
      + flags(4 BE) + drops(4 BE) + timestamp(8 BE)
      + H4 packet (variable)
```

Пошук TX:

1. `H4 packet type = 0x01` (HCI Command).
2. LE Set Extended Advertising Data `opcode LE = 0x2037` (`37 20`).
3. У параметрах `[handle, operation, frag_pref, data_length, data...]` дістати повне AD.
4. Знайти елемент `1B 03` і наступні 26 байтів P2.
5. Перевірити `src/dst`, `K1/K2`, обидві CRC та структуру DP.

Це дозволяє команді `seq sync-log` підвищувати лічильник тільки з реально розшифрованих пакетів, а `learn` — навчатися на відомих командах. **Звичайний файл pcap або btsnooz не підтримується**.

### Linux `tuya-beacon-mesh-p2-controller monitor`

Монітор працює через HCI_CHANNEL_MONITOR (`syscall.Socket` + `bind` на Linux); невеликий привілейований helper читає `HCI_MON_EVENT_PKT` для LE Meta Event 0x3E, subevent:

- `0x02` — legacy LE Advertising Report;
- `0x0D` — LE Extended Advertising Report.

Для кожного AD-вмісту шукається P2. Декодер не орієнтується лише на MAC, локальне ім'я чи RSSI. **Телефонні команди потрібно реально прийняти адаптером**: якщо сканер пропустив радіопакет, синхронізація не відбудеться. Linux HCI Monitor не читає внутрішній HCI потік Android безпосередньо; він бачить те, що отримує локальний адаптер.

Коли `monitor` і `on/off` користуються одним адаптером, не кожний USB контролер гарантує одночасне сканування та advertising. Для довготривалої роботи бажаний окремий адаптер hci1 для монітора або незалежне сканування.

## 14. Транспорт BlueZ та tinygo/bluetooth

### Чому НЕ `tinygo.org/x/bluetooth` як передавач точного P2

Бібліотека підтримує рекламу через Linux BlueZ D-Bus із полями `AdvertisementOptions.ServiceUUIDs`, `ManufacturerData`, `ServiceData`, `LocalName`, але не публікує Linux-метод `ConfigureRawAdvertisement([]byte)` для точного 31-байтового AD. `AdvertisementPayload.Bytes()` належить до **приймання**, а не встановлення довільних байтів при надсиланні. BlueZ також може перепакувати поле UUID. Отже, заміна P2 бінарного payload масивом UUID **не гарантує** побайтову відповідність.

`tinygo.org/x/bluetooth` надалі доречний для загальних GATT-пристроїв, сканування та платформ, де драйвер надає raw advertising. Проте **для цього P2** Linux-транспорт v5 — нативний **BlueZ kernel Management Socket**, без сторонніх Go-залежностей.

Документація API: <https://pkg.go.dev/tinygo.org/x/bluetooth>.

### Нативний BlueZ MGMT Socket (v5)

1. `socket(AF_BLUETOOTH, SOCK_RAW, BTPROTO_HCI)`.
2. `bind` до `HCI_CHANNEL_CONTROL=3`, `HCI_DEV_NONE=0xffff`.
3. Запит `Read Advertising Features 0x003D` — дізнатися кількість і зайняті інстанси.
4. Зайняти **вільний** інстанс, **не** перезаписуючи рекламу іншої програми.
5. `Add Advertising 0x003E` — передати 31 байт ADV як готовий бінарний масив.
6. MGMT flags: `0x00000001` (connectable); жодних автоматично доданих Flags/LocalName/TxPower, бо місце 31 байт уже заповнене. Це відтворює семантику колишнього `btmgmt add-adv -c -d HEX`.
7. Утримувати рекламне вікно (`-duration`, типово 500 мс), зняти інстанс `Remove Advertising 0x003F`, витримати `-gap` та перейти до наступного `seq`.
8. Після останнього кадру видалити тільки свій інстанс.

Формат payload для `Add Advertising`:

```text
[instance:1]
[flags:4 little-endian]
[duration:2 little-endian]   = 0
[timeout:2 little-endian]    = 0
[adv_len:1]                 = 31
[scan_rsp_len:1]            = 0
[adv_data:31]               = exact 02 01 FLAGS 1B 03 + frame26
```

У нативному транспорту **один** helper відкриває **один** socket на всю серію, замість запуску `btmgmt` для кожного кадру. Адаптер може мати апаратні обмеження щодо кількості рекламних інстансів. Програмне підтвердження MGMT означає «ядро прийняло інстанс», **не підтверджує** приймання або виконання команди лампою.

`-transport btmgmt` — резервний шлях із перевіреним раніше зовнішнім `sudo -n btmgmt`. Він може використовувати фіксований інстанс 1; `-clear-all` у цьому режимі явно зачіпає чужі оголошення, тому не використовуйте його без потреби.

Офіційна документація MGMT: <https://bluez.readthedocs.io/en/latest/mgmt-api/> (команди 0x003D, 0x003E, 0x003F).

## 15. Безпека, цілісність, моделі загроз

**Межі захисту:** XXTEA забезпечує зворотне шифрування 16-байтового блока при відомому ключі; але додаткове маскування XOR постійним ключем не є AEAD. Коротка CRC не замінює MAC. При відомому plaintext і K1 постійна XOR-маска K2 обчислюється без перебору (див. §9). Це характеристика описаної схеми, не загальна атака на XXTEA.

**`seq` не є криптографічним nonce усередині plaintext** в перевіреному TX-профілі; повторюваний plaintext дає повторюваний ciphertext. Змінюються відкритий заголовок і transport CRC. Реальний anti-replay у прошивці міг бути складнішим за монотонне порівняння; невідомі обмеження на окреме `src`, вікно пропусків і циклічне переповнення.

**Відстеження стану є optimistic**: відправили пакет ≠ лампа його прийняла; захопили команду телефона ≠ змінилася фізична яскравість. Навіть правильний CRC підтверджує лише валідність формату/ключів для декодера.

**Права:** файл із ключами — `0600`; файл стану, `.lock`, `.tx.lock` — права власника. Не запускайте весь CLI під root: це призведе до root-owned state. Privileged helper отримує тільки готові 31-байтові рекламні дані; ключі й конфігурацію читає непривілейований процес.

**MQTT:** опційний режим `tuya-beacon-mesh-p2-controller mqtt` використовує незашифрований MQTT 3.1.1, QoS0; він призначений для **довіреної домашньої LAN**. Не відкривайте брокер у публічний інтернет; для віддаленого доступу потрібна окрема захищена мережа або TLS-проксі. Небезпечні `raw`, `dp`, `seq`, `learn` через MQTT заборонені. Native HA Discovery/сутності **не додані**.

## 17. Відомі невизначеності

1. Чи приймає PHY6230 **кілька DP в одному 16-байтовому plaintext**; інші P2 реалізації використовують це, але зафіксовані команди саме цієї лампи були одиночними.
2. Чи приймає інші `src` та чи веде роздільний лічильник для кожного джерела.
3. Чи є коректне циклічне порівняння 16-бітного `seq` після переповнення.
4. Які DP/дані вибирають конкретну сцену, countdown, DND, music-reactive mode та інші функції.
5. Фізична відповідність 0..1000 температурним Кельвінам; діапазон 2700..6500 — лише початкове припущення.
6. Яка найкраща тривалість рекламного вікна і наскільки Bluetooth-контролер підтримує одночасне scan + advertise.
7. Чи можливі асинхронні P2-статуси з лампи; поточний монітор обробляє підтверджені TX DP-команди, не є контролером стану з ACK.

## 19. Первинне отримання ключів (v6): Cloud API та захоплення з ПК

### 19.1. Які секрети видно в BLE Advertising?

Повний рекламний P2-кадр містить відкриті адреси `src/dst`, 16-бітний `seq`, `head`, `subcmd`, байт перевірки plaintext, зашифрований блок `XXTEA(K1,plaintext) XOR K2` і транспортний CRC. **Власне `local_key` (K1) у рекламі не передається у відкритому вигляді.** З одного лише прослуховування без інших даних утиліта не обчислює K1. `beacon_key` (K2) можна відновити з відомого plaintext **лише за наявності актуального K1**, як описано в §9.

### 19.2. Отримання K1 через Tuya OpenAPI

Підтриманий авторизований endpoint:

```text
GET /v1.0/token?grant_type=1
GET /v2.0/cloud/thing/{device_id}
```

У першому запиті використовуються `client_id` (Access ID), `secret` (Access Secret) із Cloud-проєкту. На обох GET без тіла:

```text
contentHash = hexLower(SHA256(empty_body))
stringToSign = "GET\n" + contentHash + "\n\n" + requestPathWithQuery
macPayload(token) = client_id + token + timestampMillis + stringToSign
sign = hexUpper(HMAC_SHA256(secret, macPayload(token)))
```

Для `/v1.0/token` параметр `token` порожній; для `/v2.0/cloud/thing/{id}` — тимчасовий `access_token` із попередньої відповіді. У заголовки кладуться `client_id`, `t`, `sign_method: HMAC-SHA256`, `sign` і для другого запиту `access_token`. У цій реалізації `nonce` та додаткові `Signature-Headers` **не використовуються**; це дозволений варіант підпису для простих запитів.

Точки входу в Європі:

- Central Europe: `https://openapi.tuyaeu.com` (`-cloud-region eu`).
- Western Europe: `https://openapi-weaz.tuyaeu.com` (`-cloud-region we`).

Отриманий `result.local_key` перевіряється як 16-символьний ASCII K1. За прапорцем `-cloud-save` ключ оновлюється в JSON із правами 0600 та резервною копією. Якщо K1 змінився, старий K2 очищається: для нової активації потрібно провести `learn`. Без `-cloud-save` секрет не друкується. Можливі помилки відсутньої авторизації, неправильного дата-центру або простроченої підписки IoT Core (`28841002`). Цей режим потребує інтернету **лише під час отримання K1**.

### 19.3. Відновлення K2 наживо з ПК

```sh
sudo -v
tuya-beacon-mesh-p2-controller -config ./config.json -learn-out recovered.json learn live
```

Програма відкриває привілейований HCI Monitor socket Linux на вказаному адаптері, запускає BLE Scan (`btmgmt find -l`, якщо не задано `-scan=false`), розпізнає події `LE Meta Event` з subevent `0x02` (legacy ADV) або `0x0D` (extended ADV), знаходить AD-структуру `[0x1B, 0x03, frame26]` і фільтрує P2 data-команди. Унікальні кадри накопичуються до `-learn-timeout` (стандартно 120 с). Для кожного поєднання `src/dst` перевіряються кандидати з CRC відомих ON/OFF-повідомлень і K1. Визначений K2 має успішно розшифровувати **щонайменше два різних DP-повідомлення з різними `seq`** та проходити обидва CRC. Джерело/призначення визначаються з криптографічно перевіреної групи, не лише з MAC-адреси BLE.

**Обмеження:** HCI Monitor ПК отримує тільки рекламні звіти, які фізично почув *ПК-адаптер*. Він не може автоматично читати внутрішні HCI-команди Android і може пропускати радіопакети при слабкому сигналі, Bluetooth-фільтрації або конфлікті сканування/реклами. Якщо захоплення на ПК не працює, Android BTSnoop залишається альтернативою.

Код не отримує реальні ключі з HCI без наявного K1 і не перевіряє фізичне виконання команди лампою. Невідомий новий протокол, інші DP або зміна ключів можуть вимагати нового профілю й повторної перевірки.

### 19.4. Автоматичне відстеження `seq`

Після внесення перевіреного `beacon_key` в основну конфігурацію `tuya-beacon-mesh-p2-controller monitor` розшифровує прийняті реклами через K1+K2, відкидає старі/пошкоджені кадри і атомарно підвищує `last_reserved` у state, не перезаписуючи новіший optimistic light state. Сам `learn live` не змінює файлу state, доки користувач не застосує відновлений ключ. Це запобігає синхронізації на неперевірений криптографічний профіль.

Документація: <https://developer.tuya.com/en/docs/cloud/3829469013?id=Kcp2l2v9wma0m>, <https://developer.tuya.com/en/docs/iot/new-singnature?id=Kbw0q34cs2e5g>.

## 20. Отримання K1 через Smart Life QR (v7, без Tuya Developer)

Ця реалізація відтворює процедуру **`tuya-beacon-linux login`** (oLucasAguilar), спираючись на відкритий код офіційного **Tuya Device Sharing SDK**. Важливо розрізняти дві незалежні криптографічні системи:

- **BLE P2:** `local_key (K1) → XXTEA-BE`, `beacon_key (K2) → XOR` для керування лампою (розділи 4–9).
- **Sharing API:** `User Code + QR → тимчасова авторизована сесія`; кожний HTTPS-запит має `HMAC-SHA256`-підпис та `AES-128-GCM`-шифрування своїх параметрів/відповіді. Ці AES-ключі **не є** K1/K2 лампи.

### 20.1. QR-вхід

1. Користувач бере свій `User Code` у Smart Life → Me → Settings → Account and Security → User Code.
2. Запит без пароля (метод **POST**):
   `https://apigw.iotbing.com/v1.0/m/life/home-assistant/qrcode/tokens?clientid=HA_3y9q4ak7g4ephrvke&usercode=<escaped>&schema=haauthorize`
3. У полі `result.qrcode` приходить короткоживучий QR token; він відображається як `smartlife--qrLogin?token=<token>` (або `tuyaSmart--qrLogin?...`). На Linux для QR-виводу використовується `qrencode -t ANSIUTF8 -m 1` із вхідними даними через stdin.
4. Застосунок Smart Life сканує QR і **користувач підтверджує авторизацію**. Напис `Home Assistant` — очікуваний: QR використовує її **публічний** app `client_id`; це не облікові дані конкретного користувача та не приватний секрет.
5. Програма кожні 3 секунди запитує **GET** `/v1.0/m/life/home-assistant/qrcode/tokens/<token>?clientid=...&usercode=...`. Після `success=true` отримує `endpoint`, `terminal_id`, `access_token` і `refresh_token`. Токени не записуються на диск; сесія потрібна лише на час отримання ключа.

### 20.2. Підпис запиту Tuya Device Sharing SDK

Для **кожного** запиту обирається випадковий UUID `rid` (формат UUIDv4) та використовується токен `refresh_token` із щойно підтвердженої QR-сесії:

```text
hashKey = lowercase_hex(MD5(UTF8(rid || refresh_token)))          # 32 ASCII hex chars
secret0 = lowercase_hex(HMAC_SHA256(key=UTF8(rid), msg=UTF8(hashKey)))
aesKey  = UTF8(secret0[0:16])                                    # 16 ASCII bytes, AES-128
```

HTTP-заголовки запиту (у звичайному HTTP-представленні):

```text
X-appKey: HA_3y9q4ak7g4ephrvke
X-requestId: <rid>
X-sid: <empty>
X-time: <Unix milliseconds>
X-token: <temporary access_token>
X-sign: <lowercase hex HMAC>
```

Підпис містить поля саме в послідовності `X-appKey`, `X-requestId`, `X-sid` (пропустити, якщо порожній), `X-time`, `X-token`, розділені `||`; після них додаються `encQuery` і `encBody` **без** додаткових роздільників. `X-sign = lowercase_hex(HMAC_SHA256(key=UTF8(hashKey), msg=UTF8(signString)))`. Для нашого `GET` тіло відсутнє, отже `encBody=""`.

### 20.3. Шифрування параметрів та відповідей

Якщо є GET-параметри (наприклад, `{"devIds":"..."}` або `{"homeId":"..."}`):

```text
nonce = 12 printable ASCII chars (random)
C     = AES_128_GCM_Encrypt(key=aesKey, nonce=nonce, plaintext=UTF8(compact_JSON), AAD=nil)
encQuery = Base64(nonce) || Base64(C || tag16)
GET /some/endpoint?encdata=URL_ESCAPE(encQuery)
```

Для підпису використовується **первинний текст** `encQuery`, тобто рядок до percent-encoding в URL. В офіційному SDK обидві частини base64 кодуються окремо, а потім конкатенуються. Оскільки довжина nonce становить 12 байтів (кратна 3), для розшифрування результат можна декодувати одним `Base64Decode`: `nonce = decoded[0:12]`, `ciphertext_with_tag = decoded[12:]`, після чого `AES-GCM Open`. Відповідь `result` містить такий зашифрований рядок, який після GCM перевірки декодується як JSON.

### 20.4. Визначення потрібного пристрою та збереження

Спочатку викликається `GET /v1.0/m/life/ha/devices/detail` з зашифрованим `{"devIds":"<device_id>"}`. Якщо ID не повернуто, застосовується послідовність офіційного SDK: `GET /v1.0/m/life/users/homes`, потім для кожного `ownerId` викликається `GET /v1.0/m/life/ha/home/devices` із зашифрованим `{"homeId":"<ownerId>"}`. Програма приймає лише **точний** `device.id` із локальної конфігурації, не вгадує ключ за назвою чи PID.

`local_key` перевіряється на 16 ASCII-символів або 32 hex-символи. Значення не друкується. За замовчуванням `tuya-beacon-mesh-p2-controller login` зберігає ключ із правами `0600`, атомарним перейменуванням та бекапом старої конфігурації; при зміні K1 очищається K2, який слід відновити окремо через `learn live`. Прапорець `-qr-save=false` відключає зміну файлів.

### 20.5. Межі довіри

- QR **сам по собі** не містить `local_key`; він лише дозволяє користувачу явно видати тимчасовий доступ до Device Sharing API.
- Транспорт усіх cloud-запитів — HTTPS, і це **не** частина офлайнового BLE P2.
- `tuya-beacon-mesh-p2-controller login` не зберігає `access_token`, `refresh_token`, пароль або User Code. Ключ K1 — лише в приватному файлі конфігурації після успішного запиту.
- У різних Tuya-продуктах Sharing API іноді не повертає `local_key` для BLE-пристрою. Тоді залишається документований OpenAPI-маршрут `cloud local-key` або інше авторизоване джерело. Не можна вивести K1 лише з пасивного BLE ADV.
- **Відтворено за кодом SDK і перевірено локальними HTTP-тестами.** Робота QR-входу проти живої Tuya Cloud із конкретним обліковим записом власника **ще не перевірена**.

## Додаток: tuya-beacon-mesh-p2-controller v9 JSON-конфіг і MQTT

Починаючи з v9, повторів за замовчуванням немає (`controller.frames = 1`). Для підвищення надійності можна встановити `1..4`. Кожен повтор, якщо увімкнено, використовує **новий послідовний `seq`**. Параметри JSON читаються до обробки CLI і перевизначаються лише явно переданими прапорцями. Налаштування `controller`, `learn`, `qr`, `cloud`, `mqtt` зберігаються в одному файлі з `device`; його потрібно захистити правами 0600.

MQTT працює поза криптографією Tuya P2: брокер передає команду Go-контролеру, який формує DP, XXTEA/XOR та BLE Advertising за описаним вище алгоритмом. Обрані ефекти задаються через каталог DP73. HA MQTT Discovery публікує retained-конфіг `light`, включно з ON/OFF, яскравістю, RGB, температурою в Кельвінах і всіма 28 назвами ефектів.

Теми `.../state` містять **останній відправлений або пасивно спостережений стан**: вони не є ACK від лампи. HA отримує `availability` від MQTT-демона, а не від окремого двостороннього BLE-каналу. Для керування рекомендовано паралельно запускати `monitor` — він оновлює `seq` і стан при командах Smart Life, а MQTT-демон періодично зчитує цей файл. Див. `README.md` для структури тем і JSON.


## MQTT coalescing (v9.1)

MQTT commands from Home Assistant are not P2 frames. A single slider gesture can emit dozens or hundreds of different MQTT payloads. v9 synchronously sent each value, causing a radio backlog. v9.1 consumes broker traffic continuously, keeps only one latest pending value per topic, debounces slider updates, limits how long a continuous gesture can delay updates, suppresses short-interval duplicate values, and has one serial BLE worker. P2 sequence numbers are only allocated at the instant of a command actually dispatched to BlueZ. The previous locking/anti-replay rules remain unchanged. MQTT state topics are not retransmitted merely due to seq increments.


## Linux Raw HCI (v9.3) та швидкість сцен в HA

- `-transport raw-hci` використовує HCI_CHANNEL_RAW (Linux Bluetooth socket, root/CAP_NET_RAW), а не MGMT API. Привілейований helper приймає тільки вже зібраний 31B payload через stdin, без доступу до ключів/конфігурації. Адаптер на час передавання переводиться в advertising mode, і передавання вимикається при завершенні. **Raw HCI може переривати інше advertising або конфліктувати з bluetoothd; окремий hci-адаптер бажаний.**
- Реалізовані HCI `LE Set Random Address` (`0x2005`), `LE Set Advertising Parameters` (`0x2006`), `LE Set Advertising Data` (`0x2008`), `LE Set Advertise Enable` (`0x200A`) для legacy. Для extended: `LE Set Extended Advertising Parameters` (`0x2036`), `LE Set Advertising Set Random Address` (`0x2035`), `LE Set Extended Advertising Data` (`0x2037`), `LE Set Extended Advertising Enable` (`0x2039`). Визначення можливості — `Read Number of Supported Advertising Sets` (`0x203B`); відсутність підтримки означає використання legacy команд. Обидва варіанти транслюють саме 31B payload.
- `adv_interval` керує періодом advertising events (крок 0.625ms), за замовчуванням `20ms`. `duration` / `mqtt.tx_duration` задають час утримання advertising **одного** кадру. Це різні поняття.
- У MQTT `number` (`Effect Speed`) діапазон `1..100` передається у `effect/speed/set`, де робиться новий `DP73`, байт `raw[4]`, зі збереженням поточного ефекту та яскравості `raw[5]`. `effect/speed/state` формується зі спостереженого або optimistic `Light.Scene.Speed`. Поза режимом scene публікується `unknown` через `payload_reset`. Саме BLE-підтвердження приймання від лампи відсутнє.
- Реалізація Raw HCI орієнтується на MIT-проєкт https://github.com/oLucasAguilar/tuya-beacon-linux (код `tuyabeacon/radio.py`), але повністю переписана мовою Go без Python та сторонніх бібліотек.


## HA MQTT Discovery device metadata (v9.3.3)

Retained discovery topics:
- `homeassistant/binary_sensor/tuya_p2_controller_<client-id>_connection/config`: bridge device `tuya-beacon-mesh-p2-controller by AzaOne` / manufacturer `AzaOne`, firmware `9.3.3`, diagnostic MQTT connectivity sensor.
- `homeassistant/light/tuya_p2_<device-id>/config`: Tuya lamp and `device.via_device` set to the bridge identifier.
- `homeassistant/number/tuya_p2_<device-id>_effect_speed/config`: DP73 effect speed, same lamp device identity and `via_device`.

The light/number discovery `device` mapping uses `name: Smart bulb (<device-id>)`, `manufacturer: Tuya`, `sw_version` from `device.firmware`, and `hw_version` from `device.product_id` (with fallback to the old `device.hardware` config field). The lamp `model` field is intentionally omitted. Note that displaying Tuya Product ID as HA Hardware is a UI mapping, not a claim that this is an actual hardware revision. For previously verified `test-lamp`, fallback values are `1.2` and `wbl39qpt`. No live firmware detection is performed. `origin` identifies the publisher as `tuya-beacon-mesh-p2-controller` v9.3.3. The bridge's `Connection` sensor measures MQTT availability, not physical lamp connectivity.


## v9.3.4 — Home Assistant Bridge discovery в стилі Zigbee2MQTT

У `homeassistant/binary_sensor/tuya_p2_controller_<client-id>_connection/config` збережені старі topic і `unique_id`; його метадані `device` тепер описують `tuya-beacon-mesh-p2-controller Bridge` від `AzaOne`, модель `Bridge`, версія `9.3.4`. `Bridge state` читає JSON `{"state":"online|offline"}` через `{{ value_json.state }}`. У bridge є також MQTT `sensor` Version, Adapter, Transport із тієї самої `bridge/info`.

`light` та `number` використовують `device.via_device`, який посилається на `bridge.identifiers`; `availability_topic` — `tuya-beacon-mesh-p2-controller/bridge/state` з `availability_template: "{{ value_json.state }}"`. Тема bridge/state — retained і Last Will. Міст розміщується на `mqtt.topic_prefix/bridge/`, а лампа — у старому `<topic_prefix>/<device_id>/`. `bridge/devices` віддає лише власну каталогізацію пристроїв, а не Zigbee2MQTT API. Відсутні вигадані дані RSSI/LQI або readback лампи.

При перезапуску Home Assistant публікація `homeassistant/status: online` оновлює retained discovery, bridge state та відомий HA light state. Реальні MQTT-теми команд, Bluetooth транспорт, шифрування, каталоги сцен і збереження seq не змінені.
